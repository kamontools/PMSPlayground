Notification Types

แต่ละ notification มี trigger condition, suggested wording, และ timing type (instant = ทันที, timely = ช่วงเวลาที่เหมาะสม)

🧾 มิเตอร์ & ใบแจ้งหนี้
ลืมจดมิเตอร์
N-01
Timely
Trigger ใกล้วันครบกำหนดจดมิเตอร์ของรอบบิล ยังไม่มีการบันทึกมิเตอร์
เวลา แจ้งล่วงหน้า 2 วันก่อนวันครบกำหนด (weekday เท่านั้น)
Wording "ได้เวลาจดมิเตอร์แล้ว! อีก 2 วันถึงกำหนดบันทึกค่าน้ำ-ไฟรอบ [เดือน] อย่าลืมนะคะ"
Action ปุ่ม "จดมิเตอร์เลย" → deep-link ไปหน้าบันทึกมิเตอร์
ลืมแจ้งหนี้ — ยังไม่ได้คำนวณ
N-02
Timely
Trigger เริ่มรอบบิลใหม่ แต่ยังไม่ได้กด "คำนวณใบแจ้งหนี้" ภายในเวลาที่กำหนด
เวลา Weekday, ช่วงเช้า (รายละเอียดตาม project setting)
Wording "ยังไม่ได้คำนวณใบแจ้งหนี้เดือน [เดือน] มี [X] ห้องรอดำเนินการอยู่ค่ะ"
Action ปุ่ม "คำนวณเลย" → deep-link ไปหน้าคำนวณใบแจ้งหนี้
คำนวณใบแจ้งหนี้เสร็จแล้ว
N-03
Instant
Trigger ระบบประมวลผลคำนวณใบแจ้งหนี้สำเร็จ 100%
Wording "คำนวณใบแจ้งหนี้เดือน [เดือน] เสร็จแล้ว! [X] ห้อง พร้อมส่งให้ลูกบ้านได้เลยค่ะ"
Action ปุ่ม "ดูใบแจ้งหนี้" → รายการใบแจ้งหนี้เดือนนั้น
💳 การชำระเงิน & ยอดค้างชำระ
ใบแจ้งหนี้ครบกำหนดชำระ
N-04
Timely
Trigger ถึงวัน due date ของใบแจ้งหนี้ล่าสุด และยังมีห้องที่ค้างชำระ
เวลา Weekday, ช่วงเช้า ถึงวัน due date
Wording "ใบแจ้งหนี้เดือน [เดือน] ครบกำหนดชำระวันนี้แล้ว ยังมี [X] ห้องที่ยังไม่ได้ชำระค่ะ"
Action ปุ่ม "ดูรายการค้างชำระ" → รายการห้องที่ค้าง
ตรวจสอบเงินโอน
N-05
Instant
Trigger ระบบตรวจพบรายการโอนเงินเข้าบัญชีที่ยังรอการ match กับใบแจ้งหนี้
Wording "มีรายการโอนเงินเข้าใหม่ [X] รายการ รอตรวจสอบและแจ้งชำระหนี้ค่ะ"
Action ปุ่ม "ตรวจสอบ" → หน้า match รายการโอน
📒 การลงบัญชี
ลูกบ้านชำระออนไลน์ — รอลงบัญชี
N-06
Instant
Trigger ลูกบ้านชำระเงินออนไลน์สำเร็จ และระบบออกใบเสร็จให้แล้ว แต่ยังไม่ได้บันทึกบัญชี
Wording "ห้อง [เลขห้อง] ชำระเงินออนไลน์แล้ว ระบบออกใบเสร็จให้เรียบร้อย รอลงบัญชีค่ะ"
Stack ถ้ามีหลายห้องในวันเดียวกัน → stack เป็น "X ห้องชำระออนไลน์แล้ว รอลงบัญชี"
Action ปุ่ม "ลงบัญชี" → หน้าลงบัญชีรายการรับเงิน
✅ อนุมัติ & รายงาน & อื่นๆ
เงินสดย่อยรออนุมัติ
N-07
TBD
Trigger มีรายการเงินสดย่อยที่ส่งขออนุมัติแล้วรอการตอบกลับ
Wording ยังไม่ได้กำหนด — ต้องการข้อมูล flow การอนุมัติเพิ่มเติม
หมายเหตุ ต้องชัดเจนก่อนว่า "รออนุมัติ" คือใคร approves และ trigger จุดไหน
รายงานพร้อมดาวน์โหลดแล้ว
N-08
Instant
Trigger ระบบ generate รายงานสำเร็จ (เช่น รายงานประจำเดือน, รายงาน export)
Wording "รายงาน [ชื่อรายงาน] พร้อมดาวน์โหลดแล้วค่ะ"
Action ปุ่ม "ดาวน์โหลด" → download ไฟล์ทันที
ฟีเจอร์ใหม่ / ประกาศ
N-09
Timely
Trigger Deploy ฟีเจอร์ใหม่หรือมีประกาศสำคัญจากทีม
Wording กำหนดตาม content ของฟีเจอร์นั้น
หมายเหตุ ควร dismissible ได้ง่าย ไม่กวนงานประจำ

UI Components

Components ที่ต้องออกแบบและ implement ทั้งหมดในระบบนี้

⚙️
Settings Page
Page · 2 sub-sections

หน้าตั้งค่าการแจ้งเตือน แบ่งเป็น 2 ระดับ: Project-level และ User-level

Project Notification Setting
ตั้งค่าในระดับโปรเจกต์ (admin เท่านั้น)
  • 1
    Notification Type Toggle List
    เปิด/ปิดแต่ละ notification type ในระดับ project (N-01 ถึง N-09)
    required
  • 2
    Timely Notification Schedule
    กำหนดช่วงเวลา (วัน/เวลา) ที่ระบบจะส่ง timely notifications เช่น weekday 08:00–09:00
    required
  • 3
    Advance Notice Setting (มิเตอร์)
    จำนวนวันที่แจ้งล่วงหน้าก่อนกำหนดจดมิเตอร์ (default: 2 วัน)
    required
  • 4
    Notification Channel
    เลือกช่องทาง: In-app only / In-app + Email / In-app + LINE OA (future)
    optional
User Preference Setting
ตั้งค่าส่วนตัวของแต่ละ user
  • 1
    Personal Subscribe/Unsubscribe per Type
    user เลือกได้ว่าจะรับ notification ประเภทไหนบ้าง (ภายใต้ขอบเขตที่ project เปิดไว้)
    required
  • 2
    Do Not Disturb (DND) Hours
    กำหนดช่วงเวลาที่ไม่รับแจ้งเตือน timely (เช่น หลัง 18:00 และก่อน 07:00)
    required
  • 3
    Toast Preference
    user เลือกได้ว่าต้องการเห็น toast popup หรือแค่ notification badge เฉยๆ
    optional
🗂️
Notification Sheet
Drawer / Bottom Sheet · Full notification center

Panel ที่เปิดขึ้นมาเมื่อ user กดไอคอน bell แสดงรายการ notification ทั้งหมด

  • 1
    Sheet Header
    ชื่อ "การแจ้งเตือน" + จำนวน unread badge + ปุ่ม "อ่านทั้งหมด" + ปุ่ม settings (ไป Settings Page)
    required
  • 2
    Notification Item Row
    icon ตาม type · title · body text · timestamp · unread dot · action button (optional)
    required
  • 3
    Stacked Notification Item
    Item ที่รวม N รายการประเภทเดียวกันในวันเดียวกัน แสดง summary + expand/collapse รายละเอียด
    required
  • 4
    Date Group Separator
    แบ่งกลุ่มด้วย label "วันนี้" / "เมื่อวาน" / วันที่
    required
  • 5
    Empty State
    แสดงเมื่อไม่มี notification ใดๆ
    required
  • 6
    Swipe-to-Dismiss (mobile)
    swipe left บน item เพื่อ dismiss
    optional
🔔
Notification Toast — Single
Component · Overlay · Auto-dismiss

Toast เดี่ยวสำหรับ 1 notification สำคัญ ขึ้นมาทางขวาบนหรือล่าง

  • 1
    Icon ตาม notification type
    color-coded ตาม severity / category
    required
  • 2
    Title + Body
    title 1 บรรทัด, body max 2 บรรทัด (truncate)
    required
  • 3
    Action Button (optional)
    CTA primary เช่น "จดมิเตอร์เลย", "ตรวจสอบ"
    optional
  • 4
    Dismiss Button (×)
    ปิด toast ทันที
    required
  • 5
    Auto-dismiss Timer
    หายไปอัตโนมัติใน 5–8 วินาที (pause เมื่อ hover)
    required
🗃️
Notification Toast — Stacking
Component · Overlay · Multiple toasts

เมื่อมี toast หลายอันพร้อมกัน จะ stack ซ้อนกันแบบ deck of cards

  • 1
    Toast Stack Container
    รวม toast หลายอันในจุดเดียว ซ้อนกันด้วย offset + scale
    required
  • 2
    Collapsed Count Label
    แสดง "+2 more" เมื่อมี toast ซ่อนอยู่ด้านหลัง
    required
  • 3
    Expand on Hover/Tap
    펼 stack ออกให้เห็นแต่ละ toast แยกกัน
    required
  • 4
    Dismiss All
    ปุ่ม "ปิดทั้งหมด" เมื่อ expand stack
    optional
  • 5
    Max Visible Cap
    แสดงสูงสุด 3 toast พร้อมกัน ที่เหลือ queue
    required

UX Decisions

Anti-overwhelm Strategy — ไม่ให้ user จมกับแจ้งเตือน

กลยุทธ์ รายละเอียด ใช้กับ
Stacking notification ประเภทเดียวกัน วันเดียวกัน → รวมเป็น 1 รายการ N-06 (ชำระออนไลน์), N-05 (โอนเงิน)
Timely Batching ส่งแจ้งเตือนเฉพาะช่วงเวลาที่กำหนด ไม่ส่งกลางดึก N-01, N-02, N-04, N-09
Weekday Only timely notifications ส่งวันทำการเท่านั้น (จ–ศ) ทุก timely type
User Opt-out user เลือก unsubscribe แต่ละประเภทได้ใน User Preference ทุก type
DND Hours user ตั้ง "ห้ามรบกวน" ช่วงเวลาที่ต้องการ ทุก type (ยกเว้น critical)
Toast Limit แสดง toast พร้อมกันได้สูงสุด 3 อัน ที่เหลือ queue Toast component

Timing Matrix — Instant vs Timely

Notification Type เวลาที่ trigger เหตุผล
ลืมจดมิเตอร์ (N-01) Timely ล่วงหน้า 2 วัน, เช้า weekday ให้เวลาเตรียมตัวไปจดจริง
ลืมแจ้งหนี้ (N-02) Timely ต้น cycle, เช้า weekday เป็นงาน scheduled ต้องทำในจังหวะที่ถูก
คำนวณเสร็จ (N-03) Instant ทันทีที่ระบบประมวลผลเสร็จ user รอผลอยู่ ต้องแจ้งเร็ว
ครบกำหนดชำระ (N-04) Timely วัน due date, เช้า weekday ต้องตามทันวันนั้น ไม่ต้องรีบก่อนหน้า
ตรวจสอบโอนเงิน (N-05) Instant ทันทีที่ระบบตรวจพบ เงินเข้า ต้อง match ไว ลดความเสี่ยงผิดพลาด
ชำระออนไลน์ (N-06) Instant ทันทีที่ระบบออกใบเสร็จ ลงบัญชีทันที ข้อมูลไม่ค้าง

Stack Notification Logic

กฎการรวม, การเรียงลำดับ, และ lifecycle ของ notification ที่ถูก stack

การรวม (Grouping Rule)
  • 1
    Group Key = Type + Date
    notification จะถูกรวมก็ต่อเมื่อ เป็นประเภทเดียวกัน (เช่น N-06) AND เกิดขึ้นในวันปฏิทินเดียวกัน
  • 2
    Summary Wording เปลี่ยนตาม count
    1 item → "ห้อง 101 ชำระออนไลน์แล้ว" / 2+ items → "[X] ห้องชำระออนไลน์แล้ว รอลงบัญชี"
  • 3
    Expandable Detail
    กด expand เพื่อดูรายการย่อยทีละห้อง พร้อม action button แยกแต่ละรายการ
การเรียงลำดับ (Ordering & Bubble-up)
  • 1
    ใหม่อยู่บนสุด
    notification ที่มี update ล่าสุดจะถูก bubble ขึ้นด้านบน (sort by last_updated DESC)
  • 2
    Update เข้า → กลุ่มเดิม bubble ขึ้น
    ถ้ามี item ใหม่เข้ากลุ่มที่มีอยู่แล้ว กลุ่มนั้นจะขยับขึ้นด้านบน count ใน badge เพิ่มขึ้น
  • 3
    Counter Reset หลัง Read
    เมื่อ user กด mark-as-read บนกลุ่ม → counter ใน badge รีเซ็ตเป็น 0 สำหรับกลุ่มนั้น update ใหม่หลังจากนี้จะนับใหม่จาก 1
  • 4
    Unread → นับสะสม
    ถ้าไม่ได้กดอ่าน ระบบนับต่อเรื่อยๆ ตาม update ที่เข้ามา ไม่มีวันหมดอายุ (จนกว่าจะ read หรือ dismiss)
Lifecycle & Expiry
  • 1
    กลุ่มวันนี้ → ถูก archive เมื่อผ่านวัน
    เมื่อ midnight ผ่านไป กลุ่ม notification ของวันก่อนหน้าจะถูกย้ายไปใน "ก่อนหน้า" section (ไม่ลบ แต่ collapse)
  • 2
    ไม่สร้าง group ข้ามวัน
    N-06 วันจันทร์ และ N-06 วันอังคาร = คนละ group ไม่รวมกัน
  • 3
    Retention Policy (TBD)
    ยังไม่กำหนด — อาจเก็บ 30 วัน หรือ จนกว่า user dismiss — ต้องหารือเพิ่มเติม
กลุ่ม notification ถูก archive เมื่อผ่านวัน แต่ไม่ถูกลบ user ยังเลื่อนขึ้นไปดูประวัติย้อนหลังได้

Toast Logic

กฎว่าเมื่อไหร่ toast ถึงจะขึ้น ระยะเวลา และพฤติกรรมเมื่อมีหลายอัน

เงื่อนไขที่ toast จะขึ้น
  • 1
    Instant notifications → ขึ้น toast เสมอ (ถ้า user ไม่ได้ opt-out)
    N-03, N-05, N-06 — เพราะต้องการ action ทันที
  • 2
    Timely notifications → ขึ้น toast เฉพาะเมื่อ user อยู่ใน app
    N-01, N-02, N-04 — ถ้า user ไม่ได้เปิด app อยู่ → ส่งเป็น push notification แทน (mobile)
  • 3
    ไม่ขึ้น toast ระหว่าง DND Hours
    toast queue และจะขึ้นครั้งถัดไปที่ user กลับมา active หรือผ่าน DND window
Toast Queue & Auto-dismiss
  • 1
    Queue — แสดงทีละ 1 (single) หรือสูงสุด 3 (stacking)
    toast ที่เกินจะ queue ไว้ ขึ้นมาหลังจาก toast ก่อนหน้า dismiss
  • 2
    Auto-dismiss: 5 วินาที (default) / 8 วินาที (มี action button)
    pause timer เมื่อ user hover หรือ focus บน toast
  • 3
    Toast ไม่ = Notification อ่านแล้ว
    auto-dismiss toast ≠ mark-as-read ใน notification sheet — user ต้องกดใน sheet หรือกด action button เพื่อ clear
การปิด toast อัตโนมัติ ไม่ได้ทำให้ notification หายไปจาก sheet — มันยังอยู่ใน notification center รอ user กลับมาดู

Open Questions
ประเด็นที่ยังต้องหารือ
  • N-07 เงินสดย่อยรออนุมัติ: flow การ approve เป็นอย่างไร? ใครเป็น approver? trigger จาก event ไหนของระบบ?
  • Wording ภาษาที่ใช้ควรเป็น ราชการ / สุภาพ / เป็นกันเอง? ใช้ "ค่ะ" "ครับ" หรือ neutral?
  • Retention notification history เก็บนานแค่ไหน? 30 วัน / ตลอดไป / ลบเมื่อ read?
  • Priority ถ้ามี toast หลายอันพร้อมกัน instant vs timely → instant ขึ้นก่อนเสมอ? หรือ FIFO?
  • Channel Phase 1 = in-app only ก่อน? หรือรวม push notification (mobile) พร้อมกัน?
  • Permission user role ไหน (admin / staff / view-only) เห็น notification ประเภทไหนได้บ้าง?
